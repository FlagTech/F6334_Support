# 兩個大型任務就耗盡 Sol Ultra 額度？深度研究報告

> 研究日期：2026-07-22  
> 核心問題：兩個大型任務是否可能快速耗盡 Sol Ultra 額度？若可能，真正消耗額度的因素是什麼？  
> 研究範圍：原始 Reddit 案例、OpenAI 官方產品說明、Codex 額度與 token 計價資料，以及可重現的驗證方法。

---

## 一、結論摘要

「只做兩個任務就耗盡額度」聽起來異常，但原貼文描述的並不是兩次簡短問答，而是兩個大量讀寫、反覆比對與長篇輸出的工作：

1. 分析並整合約 10 份 PDF，產出約 700 頁的綜合文件。
2. 整理及清理約 700 個 Obsidian Markdown 檔案。

因此，以「任務數」衡量用量會嚴重失真。比較合理的單位是：實際輸入 token、快取輸入 token、輸出 token、代理數量、工具呼叫次數、重試次數，以及每一輪是否重新帶入大型上下文。

研究後可下列四項結論：

- **情況在技術上合理，但原貼文不足以證明「Sol Ultra 固定只能用 12 分鐘」或「所有 Plus 使用者都只能完成兩項大型任務」。**原文沒有提供額度頁面截圖、token 紀錄、任務執行介面、重試次數或重設週期。
- **Ultra 的設計本來就可能以較高 token 用量換取更強的協作式推理。**OpenAI 對 GPT-5.6 的說明指出，ultra 會預設協調四個代理平行工作；平行化能縮短等待時間，卻不等於減少總運算量。
- **在目前 Codex rate card 中，Sol 的輸出 token 比未快取輸入 token 昂貴得多。**Sol 每 100 萬 token 的參考費率為 125 credits（輸入）、12.5 credits（快取輸入）與 750 credits（輸出）。如果任務要求產出數百頁內容，輸出本身就可能成為主要消耗來源。
- **兩項工作都屬於「批次資料轉換」，不是 Ultra 最容易展現成本效益的工作類型。**更穩健的作法是先盤點、抽樣、建立規則，再分批處理；把 Ultra 留給架構設計、衝突判斷與最終品質檢查。

最精確的表述應是：

> 兩個大型任務確實可能大量消耗 Sol Ultra 額度，但「兩個」不是原因；真正原因可能是巨量上下文、長篇輸出、多代理平行運作、反覆工具呼叫與重試。原貼文只能證明作者的主觀使用經驗，不能單獨推導出通用額度上限。

## 二、原始案例究竟說了什麼

原始 Reddit 貼文標題是「GPT-5.6 Sol Ultra is impressive for the 12 minutes it works」，作者表示自己是 Plus 訂閱者，並描述兩項工作：

### 任務 A：PDF 整合

- 輸入：約 10 份 PDF。
- 目標：分析、合併並整理成一份完整文件。
- 作者聲稱的產出：約 700 頁。
- 結果：作者表示這項工作消耗了可用額度。

### 任務 B：Obsidian 知識庫整理

- 輸入：約 700 個 Markdown 檔案。
- 目標：整理、清理 Obsidian vault。
- 結果：作者表示第二項工作再次快速用盡額度。

### 原文沒有交代的關鍵資訊

原貼文缺少下列資訊，因此無法重建精確用量：

- 使用的是 ChatGPT、ChatGPT Work、Codex 桌面版、Codex CLI，或其他介面。
- 畫面上的完整模型名稱、推理等級與 ultra 設定。
- 工作開始前與結束後的剩餘額度。
- 額度是 credits、滾動使用上限、每日上限、每週上限，或暫時性速率限制。
- PDF 的實際文字量、圖片比例、是否需要 OCR，以及每份檔案大小。
- 700 個 Markdown 檔案的總字數、平均長度、附件數與連結密度。
- 代理實際開啟幾個子任務、呼叫多少次工具，以及是否出現失敗或重試。
- 700 頁是由模型一次產生、分段產生，還是包含大量原文內容與既有材料。
- 「12 分鐘」是計時結果、概略感受，還是標題中的修辭。

這些缺口不代表作者的經驗不可信；它們代表這則案例只能作為「異常用量線索」，不能直接當成可重現的產品限制。

## 三、先釐清 Sol、Ultra、Plus 與使用介面

### 3.1 Sol 是模型層級，Ultra 是推理與代理運作強度

OpenAI 將 GPT-5.6 Sol 定位為處理複雜程式設計、知識工作與研究工作的高能力模型。Ultra 則代表更高強度的運作方式；官方 GPT-5.6 說明指出，ultra 會預設協調四個代理平行工作，以更多 token 換取更強的結果與較短的完成時間。

這帶來一個容易忽略的差異：

- 使用者看到的是一項工作。
- 系統內部可能拆成多個代理、工具呼叫與整合步驟。
- 牆上時間可能縮短，但總 token 不一定下降。

因此，「12 分鐘」即使時間紀錄正確，也不能直接解讀成「只做了 12 分鐘的運算」。四個代理同時執行 12 分鐘，與單一代理執行 12 分鐘，資源需求並不相同。

### 3.2 Plus 是訂閱方案，不是無上限運算承諾

OpenAI 的說明指出，Codex 可隨 ChatGPT Plus、Pro、Business、Enterprise 等方案使用，但實際上限會受方案、工作區、模型、工作大小與使用介面影響。較大的程式庫、較長的工作與延伸工作階段會使用更多額度。

官方也說明，部分代理型產品可能共用 agentic usage 與 credits。這表示使用者看到的剩餘額度，未必只反映眼前這一項工作；同一帳號在其他支援介面上的使用，也可能影響共用額度池。

### 3.3 ChatGPT 與 Codex 的模型選項不能直接互換

目前官方說明中，標準 ChatGPT Plus 的 GPT-5.6 推理選項與 Codex 可選的模型及推理等級並不完全相同。Codex 可提供 Sol、Terra、Luna 等模型，而實際可用等級及額度依方案與工作區而異。

因此，看到「Plus + Sol Ultra」時，不能只根據 ChatGPT 對話介面的限制推論；必須先確認作者在哪個產品介面執行工作。

## 四、額度不是單一概念

使用者口中的「額度」可能指不同機制。若未先辨識是哪一種，就容易把暫時限制誤認為永久耗盡。

### 4.1 訊息或工作次數上限

某些產品以訊息或工作次數顯示使用限制，但每次工作的內部成本可能差異極大。一項簡短問答與一次掃描 700 個檔案的工作，即使都算「一項」，資源需求仍可能相差數個數量級。

### 4.2 滾動時間窗限制

限制可能依數小時或數天的滾動時間窗重設。此時「用完」代表需等待重設，不等同帳號永久失去功能。

### 4.3 Credits 餘額

Codex 目前提供以 token 為基礎的 credits 計算方式。實際扣除量取決於模型、輸入、快取輸入與輸出，而不是只看工作數量。

### 4.4 速率限制

短時間內平行呼叫過多，可能碰到速率限制。這種情況與總 credits 耗盡不同，稍後重試可能恢復。

### 4.5 上下文與單次輸出限制

模型的上下文視窗與單次最大輸出也是技術限制，但它們不是訂閱額度。GPT-5.6 Sol 的 API 規格列出約 105 萬 token 上下文視窗與 128K 最大輸出；這些是 API 模型規格，不能直接當成 Plus 或 Codex 的可用配額。

## 五、Codex credits 如何計算

依 OpenAI 目前公布的 Codex rate card，GPT-5.6 Sol 的參考費率如下：

| token 類型 | 每 100 萬 token 的 credits |
| --- | ---: |
| 未快取輸入 | 125 |
| 快取輸入 | 12.5 |
| 輸出 | 750 |

GPT-5.6 Terra 的同類參考費率為 62.5、6.25 與 375 credits，約為 Sol 的一半。官方同時提醒，實際使用量會依工作大小、模型與推理強度而變化。

### 5.1 基本估算式

若某項 Sol 工作的用量已知，可用下式理解 credits 的構成：

```text
Sol credits
= 未快取輸入 token ÷ 1,000,000 × 125
+ 快取輸入 token ÷ 1,000,000 × 12.5
+ 輸出 token ÷ 1,000,000 × 750
```

這是依官方 rate card 建立的說明式，不代表 Reddit 作者當時一定使用相同介面或看到相同計價方式。

### 5.2 純示例：為什麼長輸出特別昂貴

假設一項工作使用：

- 50 萬個未快取輸入 token。
- 10 萬個輸出 token。

則估算為：

```text
輸入：0.5 × 125 = 62.5 credits
輸出：0.1 × 750 = 75 credits
合計：137.5 credits
```

雖然輸出 token 只有輸入的五分之一，卻比輸入消耗更多 credits。這說明「產出 700 頁」可能比「讀取 10 份 PDF」更值得關注。

另一個純示例：

- 200 萬個未快取輸入 token。
- 20 萬個輸出 token。

```text
輸入：2 × 125 = 250 credits
輸出：0.2 × 750 = 150 credits
合計：400 credits
```

這兩組數字只用來說明費率關係，不能用來反推原貼文的真實消耗。原作者沒有公開 token 紀錄，頁數與檔案數也不能可靠換算成 token。

### 5.3 快取為何重要

同一段大型上下文若能命中快取，輸入費率可明顯降低；若每輪提示都改變前段內容、檔案排序或系統指示，使快取無法重用，重複讀取的成本就可能回到未快取輸入費率。

長工作階段常見的成本來源不是第一次讀取，而是後續每一輪都再次附帶：

- 相同的任務規則。
- 相同或高度重疊的來源內容。
- 前面累積的工具輸出。
- 代理間的中間報告。
- 已產生的大段草稿。

因此，快取命中率、提示前綴穩定性與上下文裁切方式，會直接影響同一工作能做多少輪。

## 六、任務 A：10 份 PDF 為何可能大量消耗額度

### 6.1 「10 份」不是實際工作量

PDF 數量只表示容器數，不能代表內容量。真正影響負載的是：

- 每份 PDF 的文字 token 數。
- 是否包含掃描頁面、表格、圖表與腳註。
- 是否需要 OCR 或視覺理解。
- 是否要逐段引用、比對與去除重複。
- 是否要維持原有章節、格式與參考資料。
- 產出是否要求接近來源總長度。

十份各 10 頁的文字型 PDF，與十份各 300 頁、含掃描表格的 PDF，是完全不同的工作。

### 6.2 「整合」不是一次摘要

要產出一份可信的綜合文件，代理可能需要多輪處理：

1. 解析每份 PDF。
2. 建立章節與來源索引。
3. 找出重複、矛盾與缺漏。
4. 決定保留哪些版本。
5. 產生各章草稿。
6. 將章節合併並統一術語。
7. 檢查引用、交叉參照與格式。
8. 修正前後不一致之處。

每一輪都可能重新讀取部分來源、先前摘要或草稿。若使用四個代理平行分工，還會增加任務分派、中間結果回傳與最終整合的 token。

### 6.3 700 頁是最強的消耗訊號

頁數不是可靠的 token 單位，因為字型、行距、圖表與語言都會改變每頁內容量。然而，700 頁仍清楚表示作者要求極長的輸出。

在 Sol 的 Codex rate card 中，輸出 token 費率是未快取輸入的 6 倍，也是快取輸入的 60 倍。只要產出真的接近 700 頁，輸出就可能是主要消耗來源，而非 PDF 上傳本身。

### 6.4 單次產生與分批產生的差異

GPT-5.6 Sol 的 API 規格列出單次最大輸出 128K token。若完整文件超過單次輸出能力，系統只能採分段、工具寫入或多輪產生。每增加一輪，就可能再次帶入章節摘要、格式規則與前文，進一步增加總 token。

因此，「最後得到一份文件」不代表背後只有一次模型回應。

### 6.5 非企業方案的 PDF 視覺限制

OpenAI 的 PDF 視覺擷取說明指出，對 PDF 內嵌圖片與圖表的完整視覺擷取目前限 Enterprise；其他方案主要採文字型擷取。若來源依賴圖表，模型可能拿不到完整資訊，使用者就可能反覆補充截圖、修正要求或重跑工作。這會增加用量，也可能降低整合品質。

## 七、任務 B：700 個 Markdown 檔案為何也很昂貴

### 7.1 檔案數仍不是 token 數

700 個檔案可能是 700 則短筆記，也可能是數百萬字的完整知識庫。還必須考慮：

- YAML front matter。
- 雙向連結與嵌入語法。
- 標籤、別名與路徑。
- 附件及圖片。
- 重複筆記、孤立筆記與失效連結。
- 重新命名後對其他檔案的連鎖影響。

「整理」若包含重新命名、移動、合併、拆分與更新連結，本質上是全庫關聯變更，不只是文字潤飾。

### 7.2 全庫一致性會引發多輪掃描

安全整理 Obsidian vault 通常至少需要：

1. 建立完整檔案清單。
2. 解析標題、標籤與連結。
3. 找出命名衝突及重複內容。
4. 產生變更規則。
5. 套用小批次變更。
6. 再次掃描失效連結與重複項目。
7. 檢查變更前後差異。
8. 視結果回復或重試部分操作。

如果每個階段都把大量檔案內容送入模型，總輸入會遠高於「讀 700 個檔案一次」。

### 7.3 Ultra 的平行化可能放大重複上下文

四個代理若各自負責一批檔案，理論上可以縮短等待時間；但每個代理仍需知道共同規則、資料夾架構與跨批次命名原則。若共享內容被重複傳送，總 token 可能隨代理數上升。

不能直接假設「四個代理等於四倍成本」，因為實際系統可能共享快取、裁切上下文或採不同分工。不過，也不能把平行執行當成免費加速。缺少執行紀錄時，只能將它列為高可能性的用量放大因素。

### 7.4 重試比首次執行更容易被忽略

大量檔案操作常見的重試來源包括：

- 檔名衝突。
- 權限或路徑錯誤。
- 工具輸出過長。
- 中途超時。
- 格式驗證失敗。
- 變更後發現大量失效連結。
- 使用者要求回復部分結果再重做。

若失敗後從大範圍重新開始，前一輪消耗不會自動消失。這也是「看起來只做一項工作」，實際卻累積多輪費用的常見原因。

## 八、最可能的消耗來源排序

以下是依原貼文描述與官方費率推得的可能性排序。這是分析，不是對作者帳號紀錄的直接觀察。

### 第一名：超長輸出

700 頁產出是最明顯的消耗訊號。Sol 的輸出費率遠高於輸入；若文件由模型大量新寫，輸出可能主導 credits。

### 第二名：大型上下文反覆帶入

PDF 整合與全庫整理都需要多輪比對。如果每輪重新附帶來源、摘要與既有草稿，累積輸入會快速成長。

### 第三名：Ultra 多代理平行運作

四個代理可能同時消耗 token，並產生額外的協調與彙整內容。它能提升成功率或速度，但未必降低總量。

### 第四名：工具呼叫、驗證與重試

大型工作很少一次成功。解析、寫入、檢查及修正都會增加工作輪次，失敗後重跑尤其昂貴。

### 第五名：共用 agentic usage 或 credits

如果同一帳號也使用其他代理型產品，剩餘額度可能不是由眼前兩項工作單獨造成。必須查看使用紀錄才能排除。

### 第六名：快取未命中

若提示前綴或內容排序經常變動，大量重複上下文可能無法享受快取輸入費率，導致實際成本顯著上升。

## 九、「12 分鐘」能否被證實

目前不能。

原貼文的「12 minutes」出現在標題，但未提供：

- 開始與停止的時間戳記。
- 額度重設前後畫面。
- 官方錯誤訊息全文。
- 對應方案的限制說明。
- 連續多次測試結果。

OpenAI 公開說明也沒有把 Sol Ultra 定義為「固定可用 12 分鐘」。官方限制通常依方案、工作區、工作大小、模型、推理強度及共享額度而異。

因此，合理結論是：

- 12 分鐘可能是作者這一次工作感受到的可用時間。
- 不能推論為所有 Plus 帳號的固定時間上限。
- 也不能排除作者在 12 分鐘內啟動了高並行、高輸出工作的可能性。

## 十、哪些說法有證據，哪些仍是推測

| 說法 | 目前判定 | 理由 |
| --- | --- | --- |
| 作者表示兩項大型工作快速耗盡額度 | 有原貼文支持 | 這是作者自述，但沒有後台紀錄佐證 |
| 兩項工作都屬於高 token 工作 | 高度合理 | 大量來源、長輸出與全庫關聯整理都會增加輸入及輸出 |
| Ultra 預設協調四個代理 | 有官方說明支持 | GPT-5.6 官方介紹明確說明 ultra 的平行代理設計 |
| Sol 輸出 token 的 credits 高於輸入 | 有官方 rate card 支持 | 目前 Codex 費率為輸出 750、未快取輸入 125 credits／百萬 token |
| 作者一定用了 4 倍 token | 無法證實 | 代理共享、快取與分工細節未公開，不能直接乘以四 |
| Sol Ultra 固定只能使用 12 分鐘 | 無證據 | 官方未公布這項固定限制，原文也沒有測量紀錄 |
| 所有 Plus 使用者做兩項大型工作都會耗盡額度 | 無法成立 | 額度依介面、方案、工作大小、輸出、重試與共享用量而異 |
| PDF 上傳數量本身造成額度耗盡 | 證據不足 | 檔案數不代表 token，長輸出與反覆處理更可能是主因 |
| 700 頁可直接換算成固定 token 數 | 不成立 | 語言、排版、圖片與表格都會改變每頁內容量 |

## 十一、更省額度且更可控的工作設計

### 11.1 PDF 整合：先索引，再寫作

建議將工作拆成以下階段：

1. **盤點**：只擷取檔名、頁數、目錄、文字量與是否含掃描頁面。
2. **抽樣**：選取少量代表章節，確認擷取品質與目標格式。
3. **來源索引**：為每份 PDF 建立章節摘要、關鍵詞與引用位置。
4. **去除重複**：先判斷內容重疊與版本關係，不急著寫完整文件。
5. **建立大綱**：由高推理模型設計章節架構與衝突處理規則。
6. **分章產出**：每次只帶入該章必要來源與固定格式規則。
7. **交叉檢查**：檢查引用、矛盾、遺漏與術語一致性。
8. **最終整合**：只帶入章節摘要與待修正清單，不重新載入全部原文。

這種設計的重點不是把同一任務拆成更多對話，而是限制每一輪的上下文、穩定可快取的前綴，並避免重複產生已完成內容。

### 11.2 Obsidian：先產生變更清單，再修改檔案

更安全的流程是：

1. 建立 vault 清單，記錄路徑、標題、標籤與所有內部連結。
2. 用明確規則找出重複、孤立與失效連結，不先大範圍改名。
3. 抽樣 20 至 30 個檔案測試規則。
4. 先輸出「預計變更清單」，讓使用者檢查。
5. 以小批次套用變更，每批完成後驗證連結。
6. 對低風險、規則明確的操作使用較省額度的模型或確定性工具。
7. 只把命名衝突、合併判斷與例外情況交給 Sol Ultra。
8. 保留版本控制或備份，以便發現問題時回復單一批次。

把「判斷」與「搬運」分開，通常比讓最高強度模型從頭包辦 700 個檔案更容易控制成本與錯誤範圍。

### 11.3 模型分工原則

| 工作類型 | 建議角色 |
| --- | --- |
| 大綱設計、矛盾判斷、跨來源推理 | Sol Ultra |
| 一般摘要、依固定格式改寫、批次分類 | Terra 或較低推理強度 |
| 檔案盤點、重新命名、連結檢查 | 確定性工具優先 |
| 最終抽樣、風險檢查、複雜例外 | Sol Ultra |

這不是官方指定的唯一作法，而是依模型成本結構與工作特性提出的工程化建議。

## 十二、如何重現並驗證這項主張

若要判斷「兩個大型任務耗盡 Sol Ultra 額度」是產品限制、工作設計問題，還是特定帳號情況，需要一個可重現實驗。

### 12.1 實驗前固定條件

記錄：

- 日期與時區。
- ChatGPT 方案與工作區類型。
- 使用介面與版本。
- 完整模型名稱及推理等級。
- 工作開始前的 credits 或剩餘額度。
- 是否同時使用其他代理型產品。
- 原始檔案總大小、總文字 token、圖片頁數與附件數。

### 12.2 建立對照組

至少測試三種方式：

#### 對照 A：Sol Ultra 一次處理

依原案例的方式，交由 Ultra 完整規劃及執行，記錄代理數、工具呼叫、時間、輸入、輸出與重試。

#### 對照 B：Sol Ultra 規劃，Terra 分批執行

由 Sol Ultra 只建立大綱、分類規則與驗證標準，再由 Terra 分批處理內容，最後交回 Sol 抽樣檢查。

#### 對照 C：確定性工具盤點，模型只處理例外

先用一般工具建立檔案清單、統計與連結圖，再把無法依規則判斷的項目送給模型。

### 12.3 每組必須測量的指標

- 任務是否完成。
- 輸入 token、快取輸入 token、輸出 token。
- credits 總量。
- 工具呼叫與失敗次數。
- 從開始到完成的時間。
- 內容遺漏率。
- 引用錯誤率。
- 格式錯誤率。
- Obsidian 失效連結數。
- 人工修正所需時間。

只比較「花了幾分鐘」會忽略品質與完整度。真正有意義的比較是：同樣驗收標準下，哪一種工作設計用較少 credits 完成，且人工修正最少。

### 12.4 判定標準

若三次以上測試都在相近用量點停止，且官方額度頁面顯示相同限制，才比較能支持「方案上限」的說法。

若一次處理耗用很高，但分批與模型分工大幅下降，則更支持「工作設計是主因」。

若同樣工作在不同日期或帳號出現明顯差異，則需進一步檢查滾動時間窗、共用 credits、系統負載或方案差異。

## 十五、最終判斷

「兩個大型任務就耗盡 Sol Ultra 額度」不是不可能，但這句話省略了最重要的分母：每項任務究竟讀了多少、寫了多少、開了多少代理、呼叫多少工具，又重試了幾次。

原案例中的兩項工作，一項要求整合多份 PDF 並產出約 700 頁文件，另一項要整理 700 個相互關聯的 Markdown 檔案。兩者都是長上下文、多步驟、可能高輸出的批次工作。再加上 Ultra 預設的四代理協調機制，短時間內出現大量用量具有技術合理性。

然而，現有證據不足以支持「Sol Ultra 固定只能用 12 分鐘」或「Plus 做兩個大型任務必然耗盡額度」。更準確的結論是：

> Sol Ultra 能處理高難度工作，但不適合把所有大量讀取、重複搬運與長篇輸出都交給最高強度模式。先盤點、抽樣、分批、限制上下文，再讓 Ultra 處理真正需要高階判斷的部分，通常更能兼顧完成度、可控性與額度效率。
